# Softmax 的存储与融合

[上一章](./reduction_softmax)用四个阶段表达逐行 Softmax：Max、Exp、Sum、Normalize。这个形式便于理解数据依赖，也便于分别实现每个阶段。但当输入有很多行时，指数矩阵 E 必须保存多久？行最大值和行和一定需要两个长度为 M 的数组吗？

本章保留同一个数学过程，改变工作完成的范围：从“整批做完一个阶段”改为“先完成一行，再处理下一行”。由此观察中间值怎样从完整张量变成行内状态，并区分存储节省、数据访问变化与实际性能。

## 1. 四阶段的中间值

基线数据关系为：

```text
X[M,N] → Max[M] → E[M,N] → Sum[M] → Y[M,N]
```

箭头简写了主依赖，X 还参与 E，E 还参与 Y。因为先为全部行计算 E，再为全部行求 Sum，然后计算全部 Y，E 会跨越求和阶段存活。Max 和 Sum 的每个元素也分别被对应整行的逐元素阶段读取。

对上一章的具体 IR 运行 One-Shot Bufferization，再做 CSE/canonicalize，实际得到四个分配：

| 分配 | 形状 | 先后用途 |
|---|---|---|
| 行最大值 | M | fill -∞、max reduction、指数阶段读取 |
| 指数结果 | M×N | 指数阶段写入、求和与归一化读取 |
| 行和 | M | fill 0、sum reduction、归一化读取 |
| 返回结果 | M×N | 归一化写入、返回给调用方 |

这是该 IR 与当前 pipeline 的实际选择。不是所有 Softmax 都必须有四个分配，也不是 bufferization 一定会自动把任意最后使用的输入当成下一输出。本例最后一个 generic 的 destination 是新 `tensor.empty`，分析按已表达的 destination 与别名协议作决定。

所有权流水线随后释放三个内部临时分配，返回结果继续存活，由调用方接管。释放能缩短分配的生命周期，但没有改变四阶段的计算组织；想减少中间结果，需要进一步调整计算与结果承载方式。

## 2. 按行调度与依赖顺序

各行互不依赖，因此可以把顺序改成：

```text
for 每一行 i:
    遍历这一行，得到 max
    再遍历这一行，计算 exp，并累加 sum
    再遍历这一行，用 sum 归一化
```

完成第 0 行后再处理第 1 行。行最大值和行和可以放在循环携带的 SSA 标量中，不必为所有行同时保存两个统计数组。

第二遍同时计算 E 和 Sum，这是一个 producer/consumer 融合：每个指数值刚产生就进入加法累积，避免为了求和再遍历一次完整的 E。归一化仍然要等到整行 sum 完成，不能看到第一个指数就立即用尚未完整的 sum 除它。

这说明融合不是把相邻代码块机械拼在一起。需要按数据何时已经可用来安排执行，并保持归约顺序及数值契约。

## 3. 输出空间作为暂存

sum 完成之前，每个指数值还不能变成最终概率。可以把它们先写进调用方提供的输出行，第三遍读取并原地归一化：

```text
第二遍后 Out[i,:] = E[i,:]
第三遍后 Out[i,:] = E[i,:] / Sum[i]
```

输出空间经历了两个阶段，不需要再额外分配完整 E。本例约定输入和输出形状相同、都是有效连续 MemRef、输出可写且不与输入重叠；调用方在函数返回后观察最终输出。采用更一般的布局或原地别名时，需要重新核对访问与覆盖顺序。

下面是完整实现；它是从算法手工推导的等价调度，用来建立融合的直观认识，不是声称上一章经过某个现成 Pass 就必然生成这段 IR。

<!-- softmax-example: row-softmax -->
```text
module {
  func.func @row_softmax(%x: memref<?x?xf32>, %out: memref<?x?xf32>) attributes {llvm.emit_c_interface} {
    %c0 = arith.constant 0 : index
    %c1 = arith.constant 1 : index
    %m = memref.dim %x, %c0 : memref<?x?xf32>
    %n = memref.dim %x, %c1 : memref<?x?xf32>
    %neg_inf = arith.constant 0xFF800000 : f32
    %zero = arith.constant 0.0 : f32
    scf.for %i = %c0 to %m step %c1 {
      %max = scf.for %j = %c0 to %n step %c1 iter_args(%acc = %neg_inf) -> f32 {
        %v = memref.load %x[%i, %j] : memref<?x?xf32>
        %next = arith.maximumf %v, %acc : f32
        scf.yield %next : f32
      }
      %sum = scf.for %j = %c0 to %n step %c1 iter_args(%acc = %zero) -> f32 {
        %v = memref.load %x[%i, %j] : memref<?x?xf32>
        %shift = arith.subf %v, %max : f32
        %e = math.exp %shift : f32
        memref.store %e, %out[%i, %j] : memref<?x?xf32>
        %next = arith.addf %acc, %e : f32
        scf.yield %next : f32
      }
      scf.for %j = %c0 to %n step %c1 {
        %e = memref.load %out[%i, %j] : memref<?x?xf32>
        %p = arith.divf %e, %sum : f32
        memref.store %p, %out[%i, %j] : memref<?x?xf32>
      }
    }
    return
  }
}
```

外层 `%i` 选择一行。第一条内层 for 的 iter_args 从负无穷开始，结果 `%max` 是整行最大值。第二条内层 for 的 iter_args 从 0 开始，每个 `%e` 同时写输出和参与累加，最终得到 `%sum`。第三条内层 for 再把输出中保存的 e 变成概率。

这三个循环的先后关系直接表达了“最大值完成后才能移位，行和完成后才能归一化”。N=0 时三个循环都不执行元素计算，延续上一章的空输出扩展约定。

## 4. 存储与访问的具体变化

只统计矩阵规模的数据访问，暂时把长度 M 的统计数组访问、初始化和所有权管理单列，两个算法的逻辑访问为：

| 实现 | 输入 X 读取 | 指数/输出中间读取 | 矩阵写入 |
|---|---|---|---|
| 四阶段基线 | max 与 exp 共 2MN | E 被 sum 与 normalize 读取，共 2MN | E 与 Y 各 MN，共 2MN |
| 按行实现 | max 与 exp 共 2MN | Out 暂存被 normalize 读取，共 MN | Out 写指数再写概率，共 2MN |

因此按行实现省掉了一次矩阵规模的读取，同时不再需要内部 E、Max、Sum 分配。指数的计算次数仍然是每元素一次，没有靠重复计算 exp 来换存储。

这张表数的是算法层面的逻辑元素访问，不是实际 DRAM 字节流量。缓存可能保留某些数据，后端也可能把标量或短向量留在寄存器。它能解释潜在收益来源，但不能据此宣布必然加速某个百分比。

还有其他选择：不保存 E，先遍历计算 sum，再重新计算 exp 进行归一化，可以继续调整暂存需求，却把指数计算变成两次。是否值得，取决于 exp 的代价、缓存行为和目标吞吐。后续设备内核还可能把整行或一个 tile 的指数保留在寄存器中，从而采用另一种存储层次。

## 5. 合法融合与数值顺序

本例按行处理没有改变行之间的数据依赖，因为各行独立；第二遍把指数生成与求和放在一起，也没有改变行内 j 从小到大的加法累积顺序。指数的输入仍是先完成的整行最大值，归一化仍使用先完成的整行和。

若将求和改成树形归约，或者在不同 tile 里形成部分和再合并，就改变了浮点加法顺序。这样的变换可能有价值，但要说明允许的数值差异，而不能仅凭实数结合律推断位级一致。

如果输入与输出部分重叠，还要检查第二遍写入是否覆盖随后仍要读取的输入。当前例子通过不重叠的接口前提排除了这一依赖；[别名与效果](../../compiler/analysis/alias_effects)提供的判断在这里就变成了实实在在的调用条件。

## 6. 两种实现的对照

实验将两份实现分别编译为 CPU 函数，对同一输入调用，并独立与 double 参考比较。10 组形状和数据条件包括大平移、均匀行、极小权重、单列、宽度 17/513 和空形状；本机这批输入上，两种实现的元素输出相同。

这与“沿同一 j 顺序、同一 f32 算术、同一 expf 实现”相符，但只记录当前观测，不提升为任意后端的位级一致承诺。实验还检查输入未改动、输出外哨兵、返回形状及行和。

调用成本也有差别：基线内部创建并返回结果，按行函数由调用方提供输出。若以后比较性能，需要明确是否把分配包含在计时范围内，并用一致的缓冲区复用策略进行公平对照。本章没有做计时，因此只给出已验证的结构、存储和数值结论。

## 7. 与后续调度的连接

按行调度已经展示了一种 fusion 的收益和条件，但当前还是顺序 CPU 实现。进一步优化可能给每行做分块、让一个 vector 处理多个列、由 GPU 线程协作求最大值和和，或者用目标专用存储暂存数据。

每一步都应该能回答：哪些输入在新位置已经可用，中间值存在哪一层，谁读取谁写入，边界如何处理，以及归约次序是否变化。学习 Transform 和目标映射后，再用可复现调度表达这些选择，不需要把本章手写循环当作最终性能实现。
