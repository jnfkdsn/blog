# 调度选择与性能解释

同样计算 `y[i]=2×(x[i]+1)`，前面已经得到标量循环、带 mask 的自动向量化，以及完整块使用向量、余块使用标量的实现。它们在选定输入上都正确，但运行时间并不相同。

本章用实际测量回答一个具体问题：为什么生成了 Vector 运算，程序仍可能更慢？我们先界定比较对象，再看机器代码和时间，最后区分已有证据与还需要测量的原因。

## 1. 三种实现的差别

| 方案 | 主循环 | 边界处理 |
|---|---|---|
| scalar | 每次一个元素 | 循环上界检查 |
| automatic | Linalg 分块 4，再向量化 | 每块计算有效数与 mask |
| split | 手工等价推导，每次四个元素 | 主循环只处理完整块，最后单独处理 0—3 项 |

三个方案使用相同输入输出接口，缓冲区连续且不重叠。没有给其中某个方案多做融合、减少算法工作量或改变浮点 fastmath 约定。split 是人工提供的合法对照，不宣称当前自动 pipeline 已经生成了它。

这里的标量也有精确定义：从 Linalg 直接降低到标量循环，再交给 `llc`。实验**没有**运行 LLVM `opt -O3` 的中端向量化 pipeline；`llc -O3` 选择较高的代码生成优化等级，不能把它写成“所有 LLVM 优化已经启用”。所以结果不是与编译器最强自动向量化能力的排名。

## 2. 计时对象与实验配置

一次 kernel 调用读取 N 个 `f32`、写出 N 个 `f32`。分配和初始化放在计时之外，计时包含 C ABI wrapper 与实际计算。预先检查正确性，再对每种方案预热 8 次；重复使用同一组缓冲区。

每个尺寸测量 9 组，每组重复调用多次，除以次数得到单次时间。每轮轮换三个方案的执行次序，降低固定先后次序的偏差；保留每组原始数据以及最小、中位、最大值。计时期间结果通过外部调用产生，计时后读取校验和，编译器没有把整项工作消除。

本次配置为：

| 项目 | 配置 |
|---|---|
| 测量日期 | 2026-10-04 |
| 工具链 | LLVM/MLIR 20.1.8；C 驱动用系统 Clang 14 `-O2` 链接 |
| 目标 | `x86_64-pc-linux-gnu`、`-mcpu=x86-64`、`llc -O3` |
| 环境报告的 CPU | AMD Ryzen 9 7945HX；Microsoft 虚拟化环境 |
| 执行 | 单线程，绑定逻辑 CPU 0；未固定物理主机频率与其他负载 |
| 时钟 | `CLOCK_MONOTONIC` |
| 长度 / 每组重复次数 | 1024 / 8192；65536 / 128；4194304 / 3 |

虽然主机报告支持 AVX2/AVX-512，编译目标有意选择通用 x86-64，以便观察缺少原生宽掩码访存时的代价。报告目标时不能用主机支持的最高指令集替代实际代码生成配置。

## 3. 实测结果

以下来自一次记录完整原始数据的运行，单位为微秒/调用，取 9 组中位数。它是这一配置下的观察，不是固定性能保证。

<!-- vector-benchmark-table -->
| N | scalar | automatic | split |
|---|---:|---:|---:|
| 1024 | 0.203 | 0.390 | 0.056 |
| 65536 | 12.354 | 25.007 | 3.126 |
| 4194304 | 921.104 | 1662.221 | 694.305 |

对于 65536 项，scalar 的最小/最大时间为 `12.276/12.787`，automatic 为 `24.700/25.592`，split 为 `3.086/3.787`。最大尺寸的 split 则在 `618.855—750.030` 微秒之间，说明只报一个最好值会遮住明显波动。

最直接的结论是：这次 automatic 比 scalar 慢，而 split 比两者快；小尺寸上的 split/scalar 差距接近四倍，大尺寸差距缩小。下一步应追问机器实际做了什么，而不是把 automatic 的结果归因于“向量化没用”。

## 4. 掩码怎样变成了实际成本

通用 x86-64 目标上，split 的完整块核心汇编为真实输出的节选：

```text
movups  (%rsi,%rdi,4), %xmm1
addps   %xmm0, %xmm1
addps   %xmm1, %xmm1
movups  %xmm1, (%rax,%rdi,4)
addq    $4, %rdi
```

一次读四项、两次四项加法、一次写四项。乘二在这份输出里转成了向量自加。标量版本则对应 `movss/addss`，每轮前进一项。

automatic 也有 `addps`，但在访问周围出现了不同结构：

```text
pcmpgtd ...       形成有效 lane 信息
movmskps ...     提取 mask 位
testb $1, ...    检查第 0 个位置
... movss ...   条件读取一个元素
testb $2, ...    检查第 1 个位置
...
addps ...       四项计算
...             再按 mask 条件写回
```

当前 lowering 在每个块都保留了掩码访问，目标代码把它落实成逐 lane 的条件读写及数据重排。因此“算术是向量”与“访存和控制也高效”不是同一个结论。即使测量的 N 恰好能被 4 整除，函数参数仍是动态 N；编译时并不知道这次调用没有余块。

split 通过算法结构把完整块与余块分开，令主循环可以使用连续向量访问。这解释了一个可见的额外成本来源。我们没有采集性能计数器或逐项消融，不能把全部时间差精确分摊给某几条分支。

## 5. 数据规模、资源与调度选择

这个计算每项只有两次浮点运算，至少读写 8 字节有用数据，名义算术强度约为 `2/8=0.25 FLOP/byte`。当数据量增大，运算本身减少的指令未必仍是主要瓶颈。

N=1024 的输入输出共 8 KiB；N=4194304 时合计 32 MiB。重复使用同一缓冲区的缓存行为会随着规模变化，实际层级流量还受写分配、预取、缓存容量和主机状态影响。上表中加速比缩小与这些因素相容，但没有硬件计数器就不能把它断言成已经证明的 DRAM 带宽瓶颈。

由此可以提出下一步可检验的假设：

| 假设 | 怎样增加证据 |
|---|---|
| 每块边界处理太贵 | 保留算法和目标，比较分离余块前后 IR、汇编与时间 |
| 目标掩码指令可以减少开销 | 在支持且允许执行的目标配置下重新编译；确认实际指令并重新测量 |
| 更宽向量会更快 | 同时观察拆分、寄存器压力、余块比例与时间，而不只改类型数字 |
| 工作集超过有效缓存后收益下降 | 增加尺寸扫描，记录工作集和计数器；区分缓存热、冷与流式场景 |

对 Matmul，tile 可以带来复用；对这个逐元素计算，tile 本身没有创造输入复用。不能把一个算法里的“增大 tile 有利”推广成所有算子的调度规律。

## 6. 正确性与性能分开判断

性能比较之前已用 11 个长度检查五种实现，包含空输入、完整块与不整除尾块；检查所有输出、输入保持及输出保护区。归约与收缩另用数值例子检查，但不混入本章计时。

这些测试没有证明任意浮点输入都逐位一致，也不允许改变 fastmath、alias 前提或形状约定后继续沿用旧结论。调度修改可能同时影响索引、有效 lane、求和次序和生命周期，应先确认契约，再比较时间。

完成一次性能实验时，至少应能连起这条证据链：输入规模与语义 → 实际变换 → 最终代码 → 计时范围 → 原始样本 → 有限结论。这样结果即使“优化后更慢”，也能帮助选择下一项工作。
