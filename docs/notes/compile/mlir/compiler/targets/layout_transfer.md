# 设备布局与数据搬运

把一个矩阵计算分给许多线程之后，还要看同一时刻它们访问哪些地址。每个线程的单独访问都合法，不代表这些访问组合起来适合设备。

本章用矩阵转置建立三层关系：矩阵的逻辑坐标、线程负责的坐标、缓冲区的实际地址。共享存储与 padding 的作用，会从这三层的冲突中自然出现。

## 1. 逻辑转置与线性地址

输入 A 为 M×N，输出 B 为 N×M，计算 `B[j,i]=A[i,j]`。两者都按行连续存储时，元素偏移分别是：

```text
A[i,j] → i*N + j
B[j,i] → j*M + i
```

如果同组相邻线程负责相邻 j，它们读取 A 的地址连续，但写 B 的地址相隔 M 个元素。把相邻线程改为负责相邻 i，则写出连续而读入跨步。

这是同一个数学转置造成的访问矛盾。只说“把 block 改成二维”还没有解决：二维线程坐标怎样线性分组、x/y 分别对应 i/j，仍然决定哪些地址由相邻参与者同时访问。

## 2. 数据分布与存储布局

用一个小坐标表把三层对应起来：

| 线程 | 负责的逻辑元素 | A 的元素偏移，N=8 |
|---|---|---:|
| t=0 | A[2,0] | 16 |
| t=1 | A[2,1] | 17 |
| t=2 | A[2,2] | 18 |
| t=3 | A[2,3] | 19 |

若把同一批线程改为 A[0,2]、A[1,2]、A[2,2]、A[3,2]，偏移就变成 2、10、18、26。矩阵的 MemRef layout 没变，变化的是线程到元素的映射。

反过来，保持线程负责的逻辑元素不变，改变底层 strides 或 padding，也会改变地址。实际 GPU 编译器中的“layout”一词可能指存储布局，也可能指元素在线程、lane、warp 间的分布；阅读项目时要先确认它使用的是哪一种或哪几种组合。

## 3. 通过局部存储调整访问方向

一种转置方案让线程先连续读一块 A，写入 workgroup tile，再从 tile 按转置关系取出，连续写一块 B：

```text
global A 的一块
    ↓ 按适合读入的线程分工
workgroup tile[row,col]
    ↓ barrier，随后改用另一组坐标读取
global B 的转置块
```

数据没有在数学上多做一次转置；局部存储充当不同线程分工之间的交换位置。它付出了额外的共享读写和同步，换取两侧 global 访问更好的组织。收益必须结合 tile 大小、目标和实测判断。

尾块也有两套边界：从 A 读取时检查输入坐标，从 tile 写往 B 时检查对应输出坐标。即使某个线程的 global load 被屏蔽，它也不能随意跳过其他线程仍需要参与的 barrier。

## 4. 共享存储中的 Bank 映射

共享存储本身也有组织约束。用一个明确限定的模型推导：32 个 bank、每个 f32 占一个 4 字节 word，bank 编号等于 word 地址模 32。该模型对应常见 NVIDIA shared-memory 分析情形；广播、多 word 访问和其他目标要另外分析。

若 tile 是 32×32、每行跨度为 32，32 个 lane 同时读某一列 c：

```text
lane t 读 tile[t,c]
word_offset = 32*t+c
bank = (32*t+c)%32 = c
```

它们访问不同 word，却全部落到同一个 bank。若每行增加一个不参与算法的 padding 元素，存储改为 32×33：

```text
word_offset = 33*t+c
bank = (33*t+c)%32 = (t+c)%32
```

此时 32 个 lane 落到 32 个不同 bank。padding 改变的是地址映射，逻辑上仍只计算 32×32 个元素。它额外占用 128 字节，而不是把输出矩阵多加一列。

这个推导只证明该访问模式在此 bank 模型下消除了同 bank 的多地址冲突。它没有证明整个 kernel 一定更快：更多共享存储可能影响驻留资源，其他访问阶段也可能有成本。硬件背景可对照 [CUDA 12.4 Shared Memory 指南](https://docs.nvidia.com/cuda/archive/12.4.1/cuda-c-best-practices-guide/index.html#shared-memory-and-memory-banks)。

## 5. 在 MLIR 中保留哪些信息

标准 MemRef 可以用 `memref<32x33xf32, #gpu.address_space<workgroup>>` 表示带 padding 的存储，访问只使用逻辑有效坐标。若使用自定义布局或视图，必须同时让消费者正确理解 strides、形状和地址空间。

thread/block ID 与索引算术表达元素分工；Vector 可以表达某个参与者处理的局部值。它们合起来构成一次访问，但仅凭任一类型都无法推出最终全体线程的内存事务。

在更专门的项目中，布局可能成为 Tensor encoding 或专门的属性，表示每个线程持有哪些元素、共享存储如何 swizzle、转换布局需要什么通信。这类表示的价值，在于让变换保留并消费分布信息；不能简单把它当成普通二维数组的行列顺序。

## 6. 从正确性到性能证据

布局修改需要两类检查。

先检查地址与内容：有效点没有遗漏、不同输出不意外重叠、padding 不被当作结果、读入后在正确的同步点消费。可以用小矩阵填入 `100*i+j`，让每个元素的来源可见。

再检查目标成本：真实代码用了什么 load/store 或专用搬运，是否引入额外 shuffle、共享存储或寄存器；测量是否覆盖尾块、不同形状与资源变化。理论 bank 编号或连续地址数不能直接写成性能提升百分比。

本课程把这层分析接到后面的 Matmul、Attention 与 Triton 项目。那里每个 tile 会被多次复用，搬运布局还必须匹配计算单元要求，选择就比转置更复杂。
