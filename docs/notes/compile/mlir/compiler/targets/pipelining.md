# 同步、异步依赖与流水

如果每个小块都等“搬完→算完”以后才开始下一个，搬运与计算资源可能轮流闲置。流水调度希望准备下一块时，同时计算当前块。但要实现这种重叠，必须先说明每块数据什么时候可用、缓冲区什么时候能再次写入。

本章从两个交替使用的输入缓冲区出发推导双缓冲。重点是依赖和资源，不把一个 async 关键字当成速度保证，也不把 host 侧复制与 kernel 内搬运混成同一种机制。

## 1. 串行分块的依赖

把第 k 块输入搬到局部存储的动作记作 Ck，使用它计算的动作记作 Kk。最基本的生产者到消费者关系为：

```text
C0 → K0 → C1 → K1 → C2 → K2
```

若只有一个缓冲区，每次复制都覆盖同一块内存，那么 K0 没有读完之前，C1 不能开始写。这里 `K0→C1` 并非数学算法要求相邻块必须顺序计算，而是由存储复用造成的约束。

这与 One-Shot Bufferization 分析读写冲突的思路相通：知道两个逻辑值可以独立计算，还需要确定它们的存储是否意外重叠，以及生命周期是否允许复用。

## 2. 两个 Slot 与复用边界

提供 slot0、slot1，让块 k 使用 `slot[k%2]`：

| 块 | 使用位置 | 搬入前必须等待 | 计算前必须等待 |
|---|---|---|---|
| 0 | slot0 | 无旧使用者 | C0 |
| 1 | slot1 | 无旧使用者 | C1 |
| 2 | slot0 | K0 已不再读取 slot0 | C2 |
| 3 | slot1 | K1 已不再读取 slot1 | C3 |

有两类不可缺少的边：

```text
Ck → Kk       数据已经准备好
Kk → C(k+2)   复用同一个 slot 前，旧消费者已经完成
```

只保留第一类边，可能让 C2 覆盖 K0 尚未读完的数据；只保留第二类边，K2 又可能读取尚未搬完的新数据。双缓冲的正确性来自完整的依赖图，不能只由 `k%2` 推出。

这里暂且假定结果写到各块独立的输出区域。如果输出也只有两个复用 slot，还要加入输出搬走完成到下一次覆盖的依赖。输入读完和输出传完可能是不同事件，生命周期应分别计算。

## 3. 一个允许重叠的安排

在资源确实支持独立搬运和计算的前提下，可以尝试下列安排。表中阶段表示依赖层次，不代表相同时间长度或实际测量：

| 阶段 | 搬运工作 | 计算工作 |
|---|---|---|
| 预热 | C0 → slot0 | 暂无 |
| 稳态 1 | C1 → slot1 | K0 读 slot0 |
| 稳态 2 | C2 → slot0 | K1 读 slot1 |
| 稳态 3 | C3 → slot1 | K2 读 slot0 |
| 排空 | 不再提交新块 | 等剩余计算完成 |

块数为 0 时不能无条件预取 C0；只有一块时没有稳态；奇数块与最后不足一块还要分别处理。这些边界比“循环里把 buffer 编号翻转”更容易遗漏。

若理想化地把每块复制时间记作 Tc、计算时间记作 Tk，稳态周期的下界受 `max(Tc,Tk)` 限制，而不是两者之和。但启动、同步、尾部和资源竞争都会增加实际时间，所以这只是设计目标，不是实现后的性能结果。

## 4. Host 异步与设备内异步

相同依赖图可以出现在不同层次，实现方式却不同：

| 场景 | 数据从哪里到哪里 | 常见表示/实现 |
|---|---|---|
| Host 提交复制和 kernel | host 内存与设备 global，或设备缓冲区之间 | `gpu.memcpy`、`gpu.launch_func`、`!gpu.async.token`，再到 streams/events |
| Kernel 内预取 tile | 设备 global 到 workgroup 存储 | 目标相关异步搬运，例如 NVGPU/NVVM 的相应操作与等待协议 |
| NPU 的搬运与计算流水 | 目标规定的片外/片上存储与计算单元 | 具体项目的搬运、事件和执行管线约束 |

Host token 表达一次提交工作何时完成；它不会自动给 kernel 内的共享存储访问加好 barrier。设备内部完成了一个异步 copy，也不意味着 host 已经可以读取最终输出。

在目标专用异步搬运里，还可能需要区分提交一组请求、等待组完成、使数据对参与线程可见、确认消费者结束等动作。不能只找一条名字含 wait 的指令就认为所有依赖都满足。

## 5. 共享存储轮转的调度反例

[四线程轮转](../../dialects/gpu/memory_spaces)提供了一个足够小的例子，可以枚举简化模型中的顺序。每个线程各有一项写 Wt 和一项邻居读取 Rt，且保证 Wt 在 Rt 前。

对八个原子事件枚举，这样的顺序共有 2520 种，其中 1432 种会让至少一项读取发生在邻居写入前。例如：

```text
W0 → R0 → W1 → R1 → W2 → R2 → W3 → R3
```

加入“所有 W 都完成后才允许 R”的 barrier 约束，所有剩下的顺序都满足数据就绪条件。这个模型只用于暴露必要依赖：它没有模拟硬件缓存、指令级调度或 GPU 内存模型，也不是设备运行测试。实际 GPU 仍依靠 barrier 等操作提供正确的执行和可见性保证。

这种反例方法同样适用于双缓冲：刻意让 C2 提早覆盖 slot0，就能检查是否缺少 `K0→C2`。先用小规模、可观察状态寻找缺失依赖，再进入复杂的目标同步实现，通常更容易定位问题。

## 6. 资源预算与流水深度

多缓冲需要更多存储。假设一个输入 tile 占 S 字节，双缓冲至少把这一项需求变成 2S；如果 A、B 两个矩阵操作数都双缓冲，就需要分别计算两者大小。

在 GPU 上，每组更多共享存储或寄存器可能降低同一 SM 可驻留的 block 数。粗略上界可由资源总量除以每组需求得到，但真实分配粒度、线程上限等还会进一步限制它。更深流水不一定能补偿下降的并发度。

同时，多阶段未必有可重叠的独立工作：若所有操作被串入同一条依赖链、运行时调用本身阻塞、数据搬运引擎不足，或者计算和搬运争用同一关键资源，缓冲区增加了也不一定缩短时间。

因此调优流水深度应同时记录正确性边界、存储需求、最终同步/搬运指令和设备时间。不同尺寸可能需要不同选择，不把“双缓冲”当作固定必选项。
