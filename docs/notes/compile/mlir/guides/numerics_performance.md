# 数值误差、边界输入与性能证据

同一个 Softmax 可以先物化指数数组，也可以按行处理；Attention 可以存完整分数矩阵，也可以维护在线状态。只要改变归约顺序、数学函数实现或数据复用，便需要分别回答两个问题：计算结果仍符合哪种约定，新的安排是否在目标环境中有效。

本章把前面算子实验的验证方法串起来。重点是设计能揭示错误的比较，而不是给所有输出套一个固定 tolerance。

## 1. 先规定输入与结果契约

以一行 Softmax 为例：

```text
m = max(x)
s[i] = exp(x[i]-m)
y[i] = s[i] / sum(s)
```

如果本实现只接受有限输入，就应在验证范围中明确这一点。NaN、正负无穷、全 mask、空行分别需要自己的语义决定，不能把它们混入随机测试后仅用宽松误差掩盖问题。

[Attention 基线](../tutorials/kernels/attention)选择有限分数和前缀 mask，全无效行返回零；在线版本跳过空块，再处理非空状态。这个约定让两实现有一致的比较对象，却不代表所有库都必须采用同一约定。

动态尺寸也属于契约：长度能否为零，两个矩阵的归约维是否相等，步长是否允许非连续布局，输入输出能否 alias。类型和 verifier 未必能证明所有运行时条件。

## 2. 参考结果需要独立依据

参考实现最好从数学定义或已确认的更简单算法出发，而不是把待测 lowering 原样翻译成另一种语言。否则同一个索引或 mask 错误可能在两边同时存在。

本系列 Softmax/Attention 使用 double 参考，对照 f32 实现；Matmul 还选择容易核对的数值及边界。double 通常减少舍入影响，但它不是无限精度真值，也不能自动验证任意近似数学函数的全部误差范围。

对于复杂状态算法，可以同时保留小规模可手算实例。在线 Attention 主例的状态由 (m,l,u) 从 (0,3,60) 更新到 (ln2,2.5,70)，结果为 28；漏掉旧分子的缩放得到 40。这项反例直接检查状态递推，不依赖大型随机数据碰巧触发。

## 3. 绝对误差与相对误差

常用判据为：

```text
abs(actual-reference) <= atol + rtol * abs(reference)
```

绝对项负责参考值接近零的情况，相对项随结果尺度变化。单用相对误差时，零附近的微小绝对偏差会显得无限大；单用固定绝对误差，又可能对大结果过严或对小结果过松。

容差应结合数据类型、计算长度、算法条件和数学函数实现选择。不要先看输出差多少，再把容差调到刚好能通过；更不能用较宽容差掩盖错行、错 mask 或漏项。

比较前还需处理非有限值。若要求结果有限，actual=NaN 应明确失败；普通浮点比较表达式可能产生不直观结果。若契约允许 NaN/Inf，应分别定义相应匹配规则，不能与有限值误差混算。

## 4. 重排为何可能改变结果

实数加法可结合，有限精度加法通常不可结合。f32 中，`(1e20 + -1e20) + 3.14` 与 `1e20 + (-1e20 + 3.14)` 可以得到明显不同结果，因为小量可能在不同位置被舍入掉。

因此并行归约、树形求和、FMA contraction、fast-math 或目标近似函数都需要与源语义约定一致。结果“看起来更接近 double”不自动证明某种改写在原 IR 的约束下合法。

[Math 章节](../dialects/math/scalar_math)中的 expm1 是另一个例子：直接 `exp(x)-1` 在很小 x 处可能产生消去误差，而专门实现可以有不同数值表现。检查操作名称相似或 LLVM lowering 成功，并不能替代这一层分析。

## 5. 输入集合围绕结构边界设计

以分块和归约为例，建议逐项改变会影响控制或存储的条件：

| 条件 | 能揭示的错误 |
|---|---|
| 0、1、恰好一块、余块 | 空循环、初值、最后一块越界或漏算 |
| 奇数尺寸、跨步/带偏移视图 | 把逻辑坐标当连续地址、错误 descriptor |
| 全相同、全负值、少数极大值 | 错误 max 初值、下溢和归一化问题 |
| mask 边界及全无效行 | 读取无效地址、错误 other、空状态除法 |
| 旧值仍被读取 | 不合法原地覆盖和别名问题 |

随机输入补充覆盖，但不能替代这些类别。合法性前提之外的输入应检查拒绝或已定义处理，不应执行可能越界的目标代码来“看看会怎样”。

还可利用算法性质辅助检查，例如在不引入溢出等额外问题的条件下，Softmax 对整体平移具有数学不变性，输出和应接近 1。性质测试是额外证据，不能替代逐元素参考：错序输出也可能满足和为 1。

## 6. 计时边界决定结论含义

数值检查通过后，再定义测量的是编译耗时、首次调用、稳态 kernel，还是包含分配/搬运的端到端路径。

CPU 计时应防止结果未使用而被优化掉，进行适当预热和多次采样，记录线程、输入规模、优化级别和目标配置。重复调用还要保证初始数据符合预期：原地累加若每次改变输入，后面的样本可能已不是同一个任务。

GPU/NPU 启动通常异步。只计 Host 提交前后的墙钟时间，很可能主要测到 enqueue；需要相应设备计时或在定义好的边界同步。如果把分配、JIT、H2D/D2H 包含进来，就应按端到端指标报告，不能与纯 kernel 数据直接混比。

多个采样最好保留分布或稳健统计，并说明噪声来源。把一次最快结果作为普遍加速比，通常不足以支持调度结论。

## 7. 把结构变化连接到性能原因

先建立可检查的假设：减少了多少数据搬运，是否增加重复计算，是否增加寄存器或片上存储，是否引入同步，余块是否降低有效工作比例。

[性能章节](../compiler/optimization/performance)提供固定 CPU 配置下的真实汇编和计时；[GPU Host/Device](../compiler/targets/host_device)提供 PTX、cubin、寄存器和 shared memory 报告。后者没有设备运行证据，因此资源数字只能解释潜在约束，不能直接推出吞吐或加速。

Profiler 用来核对假设，例如时间集中在哪个 kernel、搬运是否重叠、同步是否占主导。某个硬件计数器升高或占用率提高也不必然改善目标指标，应回到实际瓶颈和完整任务。

## 8. 报告能支持的范围

一份有用的结果至少说明：所用版本与设备、输入类别、算法前提、参考与容差、计时边界，以及观察到的变化。保留失败样本和原始记录，比只保存一个 speedup 更利于下一次改动。

本系列已经有 CPU 数值与部分 CPU 性能证据；GPU/NPU 的设备数值与性能尚未完成。这个限制不妨碍学习表示、编译与依赖，但必须保留在性能结论中。

可以先选择一项有限任务：为自己的变换加入“恰好 tile 大小加一”的输入，解释它经过哪个余块路径；再决定需要 IR 检查、数值检查还是两者。这样每个测试都有明确要观察的变化。
