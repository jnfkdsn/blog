# 回归测试与证据层次

[调试章节](./debugging)已经把失败缩到一条带标记的乘法。修复或明确限制后，需要防止以后修改代码时再次破坏这个行为。但“工具没有报错”只能说明很少的事情：它不保证正确的操作被保留，也不保证错误输入按预期失败。

本章围绕同一个教学 Pass 设计测试，再连接转换输出、数值程序和性能证据，说明每种检查能约束什么。

## 1. 把行为写成可区分的案例

教学 Pass 的契约是：只拒绝带 my.trigger 的整数乘法，其他操作按原样接受。因此至少要区分：

| 输入 | 预期行为 | 防止哪类回归 |
|---|---|---|
| 带标记的乘法 | 明确诊断并失败 | 检查被误删或错误放行 |
| 不带标记的乘法 | 成功且仍是原来的乘法 | 条件写宽，拒绝所有乘法 |
| 带标记的加法 | 成功 | 只看属性，忘记限定操作种类 |
| 无效语法 | parser 失败 | 最小复现脚本把无关失败当成目标失败 |

最后一项主要约束调试判定脚本，其余成为工具回归。测试集合对应行为分支，而不是把实现的每一行再翻译一遍。

## 2. FileCheck 检查数据关系

对于成功案例，不能只搜索输出中有没有 `arith.muli`。如果工具错误地返回输入 x，输出仍可能留下死乘法。

采用捕获变量连接输入、乘法结果与 return：

```text
// CHECK-LABEL: func.func @unmarked(
// CHECK-SAME: %[[X:.*]]: i32, %[[Y:.*]]: i32
// CHECK: %[[M:.*]] = arith.muli %[[X]], %[[Y]] : i32
// CHECK-NEXT: return %[[M]] : i32
```

X、Y、M 是 FileCheck 的文本捕获，不是源文件里必须固定的 SSA 名字。这样允许 printer 改名，同时要求数据关系保持。

`CHECK-LABEL` 划分函数范围，避免在另一函数中误匹配。`CHECK-NEXT` 只在相邻关系确实有意义时使用；给每行都加 NEXT 容易把无关打印变化变成失败。`CHECK-NOT` 的范围受相邻正向检查点影响，不等于自动检查整个输出；无序事实可以考虑 DAG，但不能借此忽略本来有要求的顺序。

## 3. 验证预期诊断

错误输入可以把预期诊断放在相应操作旁：

```text
// expected-error @+1 {{teaching restriction: marked multiply is unsupported}}
%m = arith.muli %x, %y {my.trigger} : i32
```

运行工具并加 `--verify-diagnostics`，要求出现指定位置和内容的诊断。它比“随便返回一个非零码”更精确，还能发现多出来的意外诊断。

在这种测试模式下，工具整体退出成功表示预期诊断被满足；不表示 Pass 已经接受了错误操作。教学 Pass 仍然报告失败，只是测试驱动把它作为正确的拒绝行为。

诊断文本应保留原因与关键约束，避免匹配完整绝对路径或与测试目的无关的长打印。

## 4. lit 组织命令，不替代断言

lit 从测试文件的 RUN 行启动工具和 FileCheck，按配置选择可执行文件、临时目录与测试格式。例如：

```text
// RUN: %my-opt %s --my-reject-marked-mul | %FileCheck %s
```

`%s` 表示当前测试文件，`%my-opt` 是本工程配置的替换项。另一个测试直接运行 `--verify-diagnostics`，不再把所有诊断塞进同一个 FileCheck 输出。

作者实际运行两个测试文件，覆盖带标记拒绝、普通乘法接受和无关标记接受。通过数量只是运行结果，核心证据仍是文件里约束的行为。

若需要某个工具预期失败再检查输出，可使用 lit 支持的 `not` 语义，并确认管道没有吞掉关键退出码。不能因为最后一个过滤命令成功，就认定前面的编译命令也成功。

## 5. 编译结构与数值分别验证

转换测试检查“生成了什么 IR”，执行测试检查“在选定输入上算出了什么”。两者互相补充。

例如 [1:N 转换](../compiler/conversion/one_to_many)检查 tuple 已消失、call 变为两结果、目标 Block 有两参数；C 程序再检查加法与减法结果。只查加法会被交换性掩盖顺序错误，所以附加减法作为非对称观察。

[在线 Attention](../tutorials/kernels/online_attention)还提供一个安全的错误递推：漏乘旧分子的缩放因子后，主例从 28 变成 40。这种负例证明测试能捕捉所关心的状态错误，比重复检查“输出不是空的”更有价值。

但有限数值用例不是形式化等价证明。它们应结合语义前提、边界分类和变换合法性解释。

## 6. 单元测试适合什么边界

如果错误集中在一个不依赖完整 pipeline 的 helper，例如类型 key 比较、对齐规划或分析格的 join，可以用单元测试直接检查返回值和失败分支。真实项目通常使用既有的 GoogleTest 基础设施，不必为简单文档另造框架。

[参数存储实验](../compiler/ir_definition/storage_interfaces)通过 C++ 探针核对共享身份、临时数组复制、容量拒绝和冲突 body；这些是窄接口行为证据。它们没有替代 parser/打印往返，也没有证明目标分配器的设备行为。

选择测试层次时问：如果故障再次出现，哪一层能最直接、稳定地给出原因？不要为了覆盖率把一个高层语义错误拆成大量与实现耦合的 getter 测试。

## 7. 一份可维护的回归记录

对本系列的工程，记录包括固定 commit、构建配置、完整命令、输入和输出、预期退出码，以及源码/正文哈希。它们让后续修改者知道测试过的是哪份实现。

这些记录仍有边界：parser/verifier 通过不代表生成代码已执行；对象文件生成不代表设备已启动；源码核对不代表那个外部项目已构建；计时不等于正确性。报告时保留这些区别，才能据证据选择下一步。

可以用一个有限练习检验自己的测试：让成功输出错误地返回原参数，看现有 FileCheck 是否失败；再把 interestingness 改成“任何失败都接受”，用语法错误证明这个判据过宽。练习应在副本中完成，不把错误规则留在正式实现中。
