# 特化、动态形状与编译缓存

模型进入服务后，每次请求的 batch 可能不同。第一章编译了一个 2×3 的输入，下一次变成 5×3 时，模型数学形式没变，但输出大小、循环边界和内存需求都变了。编译器需要回答：已有程序还能不能用？

本章围绕这一个变化展开。先看固定形状程序怎样得到并复用，再把维度改成符号，最后解释它与 graph break 的区别。

## 1. 特化的收益与适用范围

假设当前只处理 `x[2,7] @ weight[7,3] + bias[3]`。编译器可以直接知道：输出有 6 个元素，bias 每 3 个元素循环使用，输出连续布局的步长为 `[3,1]`。这些常量有利于简化索引、消除分支或选择实现。

利用已知输入条件生成实现，称为**特化**。特化不等于把运行输入的全部元素写进代码。这里只固定了部分结构条件，实际特征和权重仍然在调用时传入。

代价是结果有适用范围。若新的 x 是 `[5,7]`，需要生成 15 个输出元素，原来的固定循环不能直接照搬。

## 2. Guards 与多版本复用

编译缓存中的一份结果可以从概念上理解为：

```text
适用条件：输入 dtype、device、rank、相关 shape/stride、Python 状态……
执行入口：满足条件时可调用的程序
```

这些条件称为 guards。它们保护捕获与优化所依赖的假设。例如需要连续内存的实现不能仅检查 shape；同一个 `[2,7]` 张量也可能是一个非连续视图。

调用时先查已有结果。某个结果的 guards 成立，就复用它；全部不成立时，系统可能捕获新版本。超过重编译限制等条件下还可能回退，因此不能把“guard 失败”直接等同于“必然永久报错”。

下面是固定实验中用观察后端记录的结果。输入 batch 依次为 2、5、2，内积维 7、输出维 3 始终相同：

| 调用 | batch | `dynamic=False` 时累计 backend 调用数 | 解释 |
|---|---:|---:|---|
| 第一次 | 2 | 1 | 为第一组条件准备图实现 |
| 第二次 | 5 | 2 | 原先的静态形状条件不适用，准备新版本 |
| 第三次 | 2 | 2 | 可以再次使用已缓存的匹配版本 |

第三行很关键：缓存并不必然只有“最近一次形状”的程序。已经见过的条件可能仍然对应可复用版本。

本实验返回 FX `forward` 来计数，因此这里精确测量的是后端交接次数。实际机器码是否重新构建，还可能受到后端缓存影响；两者不能无条件等同。

## 3. 符号形状与共享实现

如果不同 batch 都重复编译，编译开销与缓存占用可能增长。另一种办法是让 batch 保持为运行时可变的整数 `B`：

```text
x[B,7] @ weight[7,3] → result[B,3]
输出元素数：3B
输出连续布局：stride = [3,1]
```

这仍然包含很多可推导信息。编译器虽然不知道 B 的具体值，却知道内积维必须匹配，知道最后一维是 3，也知道如何计算输出存储大小。

PyTorch 用 `SymInt` 等表示符号整数及其关系。符号维度不是“完全不知道”，而是可以进行符号运算、约束推理并在必要处生成运行时条件。

把观察实验设为：

```python
compiled = torch.compile(
    model, backend=inspect_backend, fullgraph=True, dynamic=True
)
```

同样的 batch 2→5→2 得到累计次数 1→1→1。捕获图的参数中可以看到 `torch.SymInt`，而 matmul、add、relu 的计算关系仍然相同。

这里为避免无关的相等关系，特意使用不同的示例维度 2、7、3。若多个样例维度刚好相等，符号系统可能根据观察和约束建立更多相等关系，首次理解时会增加干扰。

配套实验还使用真实 Inductor 后端执行这三个 batch，并与 eager 比较数值；计数观察和数值执行分别提供证据。

## 4. 动态形状的条件与代价

`dynamic=True` 并不保证再也不会重新编译。至少有几类变化仍可能改变问题：

**第一，程序结构依赖形状。** 如果 Python 写了 `if B > 4`，两侧采用不同算法，那么某个图可能只适用于其中一个范围。符号维度可以受范围条件保护，并不必然把两个分支都变成图内控制流。

**第二，特殊维度改变语义规则。** 维度 1 影响广播、stride 与简化，维度 0 影响空张量和循环执行。它们可能单独处理。因此本文 2→5 的实验不能推导出 0、1 也共享同一编译版本。

**第三，其他元数据变化。** dtype、设备、秩或不兼容 stride 的变化，都可能需要新的实现。动态形状只解决部分尺寸变化。

**第四，实现选择仍有适用条件。** 某种块大小或库实现可能依赖对齐、整除关系或范围。符号推理可以证明条件，也可以保留检查；无法满足时要选择其他实现。

固定形状能暴露更多常量，动态实现则有机会减少重新编译。选择哪一种要同时看请求分布、编译成本和稳态性能。对于已知的少量常见 batch，多个静态版本也可能是合理方案。

默认的 `dynamic=None` 还有自动判断和泛化策略，具体行为依赖版本与程序。本系列先显式比较 False/True，让实验只改变一项条件，再去分析默认策略。

## 5. Graph Break 与重新编译

现在保持形状不变，在程序中明确插入一个断图点：

```python
def broken(x):
    y = x.sin()
    torch._dynamo.graph_break()
    return y.cos()
```

前半段产生 `y`，后半段消费它。允许断图时，捕获器将计算组织成两段，并安排中间的 Python 继续执行。固定实验使用 `torch._dynamo.explain` 观察到两个图。

设置 `fullgraph=True` 后，同一个显式断图点触发 `Unsupported`，因为调用者要求完整捕获。

这与前面的 batch 变化属于不同问题：

| 现象 | 发生了什么 | 首先检查什么 |
|---|---|---|
| Graph break | 一次程序捕获被切成多段 | 哪一处行为不能或被要求不进入同一张图 |
| Guard miss | 当前输入不满足某个已有版本的假设 | 失败的是 shape、stride、Python 状态还是其他条件 |
| 新版本编译 | 为新的适用条件准备实现 | 新旧条件为什么不同，是否应泛化 |
| Backend 编译失败 | 已捕获的图无法被选定后端处理 | 对应 lowering、代码生成或外部编译错误 |

一个有两个图段的程序，后续可以一直复用这两个图段；一个没有断图的程序，也可能因多种形状频繁重编译。优化时要先分清现象，再选择处理方法。

## 6. 诊断顺序

定位某个函数为什么慢，可以先固定一组输入，区分首次和预热后耗时。如果稳态正常但不同请求触发明显长尾，再观察编译和 guard 信息。

这时日志命令有明确用途：

```bash
TORCH_LOGS="guards,recompiles,graph_breaks" python model.py
```

输入是实际模型脚本，输出是复用条件与失败位置。应把某次日志中的条件与输入变化对应起来，例如“第二次 batch 从 2 变 5，静态尺寸条件失败”；不能只看到大量日志就认定系统发生了严重问题。

当需要分析后端缓存，再继续看编译图、生成代码和缓存键。不要通过删除所有缓存制造一次慢启动后，把结果当作正常服务延迟。
